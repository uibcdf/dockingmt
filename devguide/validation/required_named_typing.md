# Molecular preparation requires named provider types

## Compatibility change — 2026-10-10

[DockingMT #5](https://github.com/uibcdf/dockingmt/issues/5) and
[#49](https://github.com/uibcdf/dockingmt/issues/49) own removal of the ligand and
receptor classifiers based on elements, atom/residue names and ring membership.
MolSysMT already supplies reusable AutoDock4 assignment under
[#222](https://github.com/uibcdf/molsysmt/issues/222). DockingMT now requires a valid
named assignment or explicit provider `typing_options`; it selects no replacement
model. Bare force-field labels, charge-only assignments and untyped PDB inputs
raise an actionable `ArgumentError`. Automatic Vina preparation applies the same
requirement, even with `allow_provisional_preparation=True`.

```python
prepared = dmt.prepare_ligand(
    ligand_with_declared_chemistry_and_indexed_hydrogens,
    selection='all',
    typing_options={'typing_scheme': 'autodock4', 'method': 'chemical_environment'},
)
```

Alternatively, call `msm.build.assign_autodock_atom_types` with an explicit scheme
and method before preparation. Automatic `dock(problem)` requires those
preassigned systems; the protocol does not select molecular preparation models.
The shown experimental method requires its supported declared complete chemistry
and indexed hydrogen inventory. Explicit ligand H/charge stages remain available
before typing. Receptor preparation adds no repair or H/charge stage. Provider
errors propagate unchanged. Inputs and option mappings remain detached.

Valid projected parent labels retain their original assignment and atom axis;
preparation does not reclassify fragments. Provider H/HD labels determine omitted
versus retained H. Charge transfers, PDBQT writing and source maps retain their
existing behavior pending provider #223/#214. Missing charges still produce
provisional placeholders. Named types with named charges receive the existing
**unassessed** preparation assessment, not scientific certification. Historical
prepared objects retain inspection of their declared heuristic provenance.

## Compatibility evidence and boundaries

The [pre-change paired comparison](legacy_named_typing_comparison.md) retains
23 pairs, four incomplete-input controls and its original producer/raw digests.
Its 14 changed pairs are intentional compatibility evidence; no archives or
original producer bytes are regenerated by this change.

Current torsion-matrix controls use explicit public H/type assignment on the
existing SDF/RDKit reference bridge. Original source/reference file digests, heavy
atom coordinates and identities, cuts and rigid fragments remain independently
checked. Historical generated-PDBQT digests remain in the immutable baseline;
current output includes named attribution and may change labels/H. The neutral
1S63 SDF has no donor H; its independent PDBQT reference has one extra HD.
Tests compare original-source fragments without asserting that those inventories
or generated H geometries are chemically equivalent.

The 181L integration tests reuse the previously declared provider workflow,
including HIE and charged termini. They exercise real default Vina, pose identity,
RMSD, automatic named-input preparation and result/viewer serialization. They
establish software behavior, not new scientific qualification of those hypotheses.
Original search receipts and unintegrated 5X72 displacement work stay unchanged.

Force-field charges alone do not supply all typing prerequisites: the current
1VII AMBER14 route returns 596 atoms and +2 e without declaring a complete
chemical graph. Tests now retain explicit rejection of that charge-only input;
DockingMT adds no graph-completion routine. The earlier 364-atom charge-only
export remains historical evidence on its original consumer source.

[MolSysMT #376](https://github.com/uibcdf/molsysmt/issues/376) records the public
`msm.set(MolSys, atom_ff_type=...)` adapter gap. Bare-label admission controls use
the already supported public MolecularMechanics setter, with no invented named
provenance or downstream mutation helper. That provider proposal is not a blocker.
